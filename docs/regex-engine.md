# Regex engine

API Gateway evaluates mapping-template `matches`/`replaceAll`/`split`, integration response
`selectionPattern`s, and Lambda authorizer identity validation expressions with
`java.util.regex`. `crates/apigw-regex` reproduces it by translating Java syntax to
`fancy-regex` and checking the result against the JDK fixture corpus in
`tools/java-regex-oracle`. This page records how close the translator is to Java, and why it
stays after an evaluation of the pure-Rust reimplementation
[`java_regex`](https://crates.io/crates/java_regex) (#57).

## Translator accuracy

Measured 2026-11-22 against the oracle fixtures generated by JDK 21.0.12: 707 patterns (92 of
them invalid in Java) and 10,866 checks, run by `cargo test -p apigw-regex`.

| | Translator (`fancy-regex`) |
|---|---|
| Wrong results | 42 checks across 6 patterns, all listed as divergences in `tests/java_fixtures.rs` |
| Valid patterns refused | 1: `\N{name}`, with a typed `Unsupported` error at load time |
| Invalid patterns accepted | 0 |
| Replacement strings Java rejects (`$9`, trailing `$`, unknown `${name}`) | 62 errors, as Java |

The differences that remain:

- **`\N{name}` is refused.** Resolving a character name needs the Unicode name table, about
  35,000 names. Carrying it means a dependency (`unicode_names2`, which brings `phf` and a
  build-time generator) or a generated table of roughly 1 MB in the binary, for a construct
  API definitions are unlikely to use.
- **Case-insensitive back references.** The engine compares the referenced text by Unicode
  simple case folding over the same number of UTF-8 bytes. Java compares each character
  through `toUpperCase` and `toLowerCase`, and folds only ASCII letters without `(?u)`. So
  `(?i)(é)\1` matches `éÉ` here but not in Java, while `(?iu)(.)\1` matches `k` + Kelvin sign,
  `sſ`, `ßẞ`, `iı`, and `iİ` in Java but not here. ASCII text compares as in Java.
- **`\X` in a look-behind.** Java bounds a look-behind as if `\X` had no width, so
  `(?<=\G\X)` never matches in Java; here it matches the cluster.
- **`\b{g}` and Java's matcher state.** `\b{g}` follows Java's `GraphemeBound`: a boundary is
  any position at or after the end of the first cluster that starts where the previous match
  ended. Java reads that position from matcher state that its own look-ahead and repetition
  nodes overwrite during a match; `x(?=yy)\b{g}` even throws `StringIndexOutOfBoundsException`
  on `xyy`. The translation always uses the previous match end.
- **Unicode version.** General categories, binary properties, scripts, case mappings, and
  grapheme cluster types come from the engine and the Rust standard library (Unicode 16 or
  later), where JDK 21 has Unicode 15. Characters added or changed since then can differ, for example
  `\p{IsAlphabetic}` on U+0363. Block and script names and block ranges are Java's own,
  generated into `src/tables.rs` by `tools/java-regex-oracle/tables.sh`.
- **Surrogates.** Strings are UTF-8, so neither input nor matches can split a surrogate pair:
  after an empty match the scan advances by a whole character where Java advances one UTF-16
  unit, and a lone surrogate in a pattern never matches, as in Java for any well-formed input.

How the constructs that used to be refused or wrong are translated:

- `\G` is the engine's `\G`. After an empty match Java resumes one character later while `\G`
  still means the end of that match, so the translator then searches with
  `\G(?s:.)+?\K(?:...)` from that position.
- `\X` is Java's `Grapheme.nextBoundary` written as an atomic pattern, and `\b{g}` checks that
  the text from the previous match end through the next character is not still one cluster.
  In a one-off comparison both agreed with JDK 21 on 800 random strings mixing every grapheme
  cluster type.
- `\p{javaXxx}`, `\p{IsXxx}`, POSIX classes under `(?U)` (including `Graph` and `Print`), and
  `\p{InBlock}` follow `CharPredicates` and `Character`, including Java's case-insensitive
  variants such as `(?i)\p{Lu}` matching every cased letter. In a one-off comparison of 190
  property patterns over every code point, the sets agreed with JDK 21 on every code point
  assigned in Unicode 15 except where Unicode changed the property later (U+0363–U+036F
  `Alphabetic`, U+30FB and U+FF65 `ID_Continue`, U+226D `Bidi_Mirrored`).
- Case-insensitive literals and classes under `(?iu)` are expanded to the exact characters
  Java's `SingleU`, `SliceU`, `bitsOrSingle`, and `CIRangeU` accept (so `(?iu)i` matches `İ` and
  `ı`, and a lone `ß` does not match `ẞ` while `ßa` matches `ẞa`). A one-off comparison of
  literal, run, class, range, and negated-class forms of every character JDK 21 has a case
  mapping for (14,405 patterns) agreed with JDK 21.
- A loop whose body can match the empty string runs on the engine's backtracking VM, which,
  like Java, stops at an empty iteration and keeps its groups. A greedy `(X)*` around a
  zero-width `X` with one way to match keeps no capture, as Java's `GroupCurly` does.
- Java's ASCII `\b` also counts a non-spacing mark that follows a letter or digit (through a
  chain of BMP marks) as a word character; the translation does the same, and agreed with
  JDK 21 at every position of 800 random strings of letters, digits, marks, and
  supplementary characters.

## Limits

Evaluation never turns a limit into a "no match". A match that needs more than the backtrack
limit (`RegexOptions::with_backtrack_limit`, default 1,000,000 steps) fails with
`RegexError::BacktrackLimitExceeded`, and a pattern nested more than 100 levels deep fails to
compile with `RegexError::TooDeep`. Every caller treats an error as a failure: a
`selectionPattern` that cannot be evaluated answers `500` instead of selecting another
response, an identity validation expression answers the authorizer configuration error, and a
template's `matches`/`replaceAll`/`replaceFirst`/`split` or a JSON path `=~` filter fails the
template. `long_inputs_do_not_overflow_a_worker_stack` checks that long inputs, including to
the constructs above, cannot overflow a worker stack, and
`limits_never_turn_into_a_silent_non_match` replays the `java_regex` cases below.

## Decision

**Keep the translation.** `java_regex` 0.1.0 can abort the gateway process from client input
and silently returns wrong answers when its fixed limits are hit. It is also less accurate
than the translator on our corpus, and 2–20× slower. Revisit when a release fixes the
blocking items listed under [Revisiting](#revisiting).

## Evaluation of `java_regex` 0.1.0

Measured 2026-10-10. 0.1.0 (2026-07-21) was the only published version.

### Accuracy

The oracle cases of the time (473 patterns) were replayed against both engines; the
translator column is as it was then, before the gaps above were closed. The fixtures
generated by JDK 21.0.12 and by Temurin 25.0.4.1 are byte-identical, so the JDK version
`java_regex` targets (25) does not explain any difference.

| | Translator (`fancy-regex`) | `java_regex` |
|---|---|---|
| Fixture checks (473 patterns) | 5,898 | 5,898 |
| Wrong results | 39, all documented divergences (empty final iteration, `\b` after combining marks, dotted/dotless `i`) | 43 across 8 patterns, undocumented |
| Valid patterns refused | 12, with a typed `Unsupported` error at load time | 11, as syntax errors |
| Invalid patterns accepted | 0 | 16 |
| Replacement strings Java rejects (`$9`, trailing `$`, unknown `${name}`) | 62 errors, as Java | 0: silently expanded |

`java_regex` got the translator's 39 divergent checks right, and 9 of its 12 refused
patterns (`\G`, `\X`, `\p{javaLowerCase}`, `\p{InGreek}`, lone surrogates, `(?i)` back
references). Its own errors:

- **Wrong results.** `(?i)\p{Lower}` and `(?i)\p{Upper}` ignore case; `\p{Space}` misses
  `\x0B`; `\p{IsWhite_Space}` misses U+00A0; `[&&a]` matches nothing; `(?iU)é` vs `É`,
  `(?iu)[a-z]` vs `ſ`, and `(?iu)ǰ` vs `J̌` case-fold differently from Java.
- **Accepts invalid patterns.** `\x{110000}`, `\x{41`, `\u12`, `\p{L`, `\p{Lower`,
  `\p{Letter}`, `\N`, `\y`, `\Y`, `(?<a_b>x)`, and `[\A]`, `[\B]`, `[\R]`, `[\b]`, `[\z]`,
  `[\k<a>]` inside a class.
- **Rejects valid patterns.** `\p{IsAlphabetic}`, `\p{gc=Lu}`, `\p{general_category=Nd}`,
  `\p{sc=Greek}`, `\p{script=Latin}`, `\p{block=Greek}`, `\N{LATIN SMALL LETTER A}`, `\b{g}`,
  `[a&&]`, `(?x)a + ?`, `a\Q\E+`.

### Crashes and limits

A stack overflow aborts the process whatever the panic strategy, and `catch_unwind` cannot
stop it. All of the following were reproduced on a release build.

- **Matching recurses once per repetition.** `x*`, `.*`, `\w+`, `[^,]*` and `(?:x)*` abort
  on about 4,500 characters on a 2 MiB thread, Tokio's worker default, and on about 18,000
  characters on 8 MiB. Any template that matches a request value with such a pattern lets a
  client crash every replica. The translator handles 1 MB on the same stack;
  `long_inputs_do_not_overflow_a_worker_stack` in `crates/apigw-regex/tests/never_panics.rs`
  now enforces this.
- **Parsing recurses without bound.** About 5,000 nested groups or classes abort compilation
  on 2 MiB. So do `(?:){5000}`, and `^{100000}` on any input.
- **The limits are silent and not configurable.** There is a fixed budget of 5,000,000 steps
  per call and a nesting depth of 500. Exceeding either returns "no match", never an error:
  - a 600-character literal does not match itself;
  - `(?:a|b)*` does not match 248 characters of `ab`;
  - `find("b|a")` on 3,000,000 `a`s returns 999,999 matches.

  For an identity validation expression or a `selectionPattern`, a silent "no match" is a
  wrong authorization or status decision.
- **Explicit panic sites.** None of the roughly 100 `unwrap`, `unreachable!`, slicing, and
  indexing sites is reachable from a pattern or input in a release build. Two unchecked
  multiplications in lookbehind length (`engine.rs:37`, `:49`) overflow in debug builds only,
  for example on `(?<=((a{4294967295}){4294967295}){4294967295})b`.
- **Fuzzing.** `cargo-fuzz` (3 workers, about 4 minutes, seeded with the oracle cases) ran
  every operation with arbitrary flags. `java_regex` crashed 6 times in 3.6 million runs, every
  one a stack overflow. The repo's `java_regex` target on `apigw-regex` ran 240,000 times in
  the same time with no crash.

### Performance

Release build, single thread, mean time per call:

| Case | Input | Translator | `java_regex` |
|---|---|---|---|
| compile `.*\[400\].*` | — | 103 µs | 0.6 µs |
| compile `^Bearer [-0-9a-zA-z\.]*$` | — | 165 µs | 0.9 µs |
| selection `.*\[400\].*` matches | 50 B | 169 ns | 2.9 µs |
| selection `5\d{2}` matches | 3 B | 64 ns | 306 ns |
| identity validation `^Bearer …$` matches | 1 KB | 21.8 µs | 51.0 µs |
| `replaceAll("\s+", " ")` | 1 KB / 100 KB / 1 MB | 25 µs / 2.5 ms / 23 ms | 116 µs / 11.8 ms / 111 ms |
| `split(",")` | 1 KB / 100 KB / 1 MB | 5.9 µs / 0.58 ms / 5.9 ms | 51 µs / 4.9 ms / 50 ms |
| `(?s).*Deluxe.*` matches | 1 KB / 100 KB | 2.2 µs / — | 42 µs / stack overflow |

`java_regex` compiles 50–200× faster, but every pattern is compiled once when the definition
loads and the VTL renderer caches compiled patterns. It matches 2–20× slower, partly because
every call copies the input into a `Vec<char>`.

## Revisiting

A later `java_regex` release is worth re-running through the same evaluation when it has:

1. iterative or depth-bounded matching and parsing, so that no pattern or input can overflow
   the stack;
2. a distinguishable error when a step or depth limit is hit, with configurable limits;
3. the accuracy differences above fixed, or at least documented.

A replacement still sits behind the `apigw-regex` API, keeps the typed errors and Java's
replacement-string validation, and must pass the oracle corpus and `never_panics`.
