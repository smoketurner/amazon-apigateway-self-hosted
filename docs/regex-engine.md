# Regex engine

API Gateway evaluates mapping-template `matches`/`replaceAll`/`split`, integration response
`selectionPattern`s, and Lambda authorizer identity validation expressions with
`java.util.regex`. `crates/apigw-regex` reproduces it by translating Java syntax to
`fancy-regex` and checking the result against the JDK fixture corpus in
`tools/java-regex-oracle`. This page records why the translator stays, after an evaluation of
the pure-Rust reimplementation [`java_regex`](https://crates.io/crates/java_regex) (#57).

## Decision

**Keep the translation.** `java_regex` 0.1.0 can abort the gateway process from client input
and silently returns wrong answers when its fixed limits are hit. It is also less accurate
than the translator on our corpus, and 2–20× slower. Revisit when a release fixes the
blocking items listed under [Revisiting](#revisiting).

## Evaluation of `java_regex` 0.1.0

Measured 2026-10-10. 0.1.0 (2026-07-21) was the only published version.

### Accuracy

The oracle cases were replayed against both engines. The fixtures generated by JDK 21.0.12
and by Temurin 25.0.4.1 are byte-identical, so the JDK version `java_regex` targets (25) does
not explain any difference.

| | Translator (`fancy-regex`) | `java_regex` |
|---|---|---|
| Fixture checks (473 patterns) | 5,898 | 5,898 |
| Wrong results | 39, all documented divergences (empty final iteration, `\b` after combining marks, dotted/dotless `i`) | 43 across 8 patterns, undocumented |
| Valid patterns refused | 12, with a typed `Unsupported` error at load time | 11, as syntax errors |
| Invalid patterns accepted | 0 | 16 |
| Replacement strings Java rejects (`$9`, trailing `$`, unknown `${name}`) | 62 errors, as Java | 0: silently expanded |

`java_regex` gets the translator's 39 divergent checks right, and 9 of its 12 refused
patterns (`\G`, `\X`, `\p{javaLowerCase}`, `\p{InGreek}`, lone surrogates, `(?i)` back
references). Its own errors:

- **Wrong results.** `(?i)\p{Lower}` and `(?i)\p{Upper}` ignore case; `\p{Space}` misses
  `\x0B`; `\p{IsWhite_Space}` misses U+00A0; `[&&a]` matches nothing; `(?iU)é` vs `É`,
  `(?iu)[a-z]` vs `ſ`, and `(?iu)ǰ` vs `J̌` case-fold differently from Java.
- **Accepts invalid patterns.** `\x{110000}`, `\x{41`, `\u12`, `\p{L`, `\p{Lower`,
  `\p{Letter}`, `\N`, `\y`, `\Y`, `(?<a_b>x)`, and `[\A]`, `[\B]`, `[\R]`, `[\b]`, `[\z]`,
  `[\k<a>]` inside a class.
- **Rejects valid patterns.** `\p{IsAlphabetic}`, `\p{gc=Lu}`, `\p{general_category=Nd}`,
  `\p{sc=Greek}`, `\p{script=Latin}`, `\p{block=Greek}`, `\N{LATIN SMALL LETTER A}`, `\b{g}`,
  `[a&&]`, `(?x)a + ?`, `a\Q\E+`.

### Crashes and limits

A stack overflow aborts the process whatever the panic strategy, and `catch_unwind` cannot
stop it. All of the following were reproduced on a release build.

- **Matching recurses once per repetition.** `x*`, `.*`, `\w+`, `[^,]*` and `(?:x)*` abort
  on about 4,500 characters on a 2 MiB thread, Tokio's worker default, and on about 18,000
  characters on 8 MiB. Any template that matches a request value with such a pattern lets a
  client crash every replica. The translator handles 1 MB on the same stack;
  `long_inputs_do_not_overflow_a_worker_stack` in `crates/apigw-regex/tests/never_panics.rs`
  now enforces this.
- **Parsing recurses without bound.** About 5,000 nested groups or classes abort compilation
  on 2 MiB. So do `(?:){5000}`, and `^{100000}` on any input.
- **The limits are silent and not configurable.** There is a fixed budget of 5,000,000 steps
  per call and a nesting depth of 500. Exceeding either returns "no match", never an error:
  - a 600-character literal does not match itself;
  - `(?:a|b)*` does not match 248 characters of `ab`;
  - `find("b|a")` on 3,000,000 `a`s returns 999,999 matches.

  For an identity validation expression or a `selectionPattern`, a silent "no match" is a
  wrong authorization or status decision.
- **Explicit panic sites.** None of the roughly 100 `unwrap`, `unreachable!`, slicing, and
  indexing sites is reachable from a pattern or input in a release build. Two unchecked
  multiplications in lookbehind length (`engine.rs:37`, `:49`) overflow in debug builds only,
  for example on `(?<=((a{4294967295}){4294967295}){4294967295})b`.
- **Fuzzing.** `cargo-fuzz` (3 workers, about 4 minutes, seeded with the oracle cases) ran
  every operation with arbitrary flags. `java_regex` crashed 6 times in 3.6 million runs, every
  one a stack overflow. The repo's `java_regex` target on `apigw-regex` ran 240,000 times in
  the same time with no crash.

### Performance

Release build, single thread, mean time per call:

| Case | Input | Translator | `java_regex` |
|---|---|---|---|
| compile `.*\[400\].*` | — | 103 µs | 0.6 µs |
| compile `^Bearer [-0-9a-zA-z\.]*$` | — | 165 µs | 0.9 µs |
| selection `.*\[400\].*` matches | 50 B | 169 ns | 2.9 µs |
| selection `5\d{2}` matches | 3 B | 64 ns | 306 ns |
| identity validation `^Bearer …$` matches | 1 KB | 21.8 µs | 51.0 µs |
| `replaceAll("\s+", " ")` | 1 KB / 100 KB / 1 MB | 25 µs / 2.5 ms / 23 ms | 116 µs / 11.8 ms / 111 ms |
| `split(",")` | 1 KB / 100 KB / 1 MB | 5.9 µs / 0.58 ms / 5.9 ms | 51 µs / 4.9 ms / 50 ms |
| `(?s).*Deluxe.*` matches | 1 KB / 100 KB | 2.2 µs / — | 42 µs / stack overflow |

`java_regex` compiles 50–200× faster, but every pattern is compiled once when the definition
loads and the VTL renderer caches compiled patterns. It matches 2–20× slower, partly because
every call copies the input into a `Vec<char>`.

## Revisiting

A later `java_regex` release is worth re-running through the same evaluation when it has:

1. iterative or depth-bounded matching and parsing, so that no pattern or input can overflow
   the stack;
2. a distinguishable error when a step or depth limit is hit, with configurable limits;
3. the accuracy differences above fixed, or at least documented.

A replacement still sits behind the `apigw-regex` API, keeps the typed errors and Java's
replacement-string validation, and must pass the oracle corpus and `never_panics`.
